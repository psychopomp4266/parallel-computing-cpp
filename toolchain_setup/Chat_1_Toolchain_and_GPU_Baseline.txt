8. WHY "cl" WAS NOT INITIALLY FOUND
====================================================================

Running:

    cl

in an ordinary PowerShell did not work.

This was not an MSVC installation failure.

MSVC is not designed to be used simply by permanently putting one
compiler directory into the global PATH.

Visual Studio has a larger environment consisting of variables and
paths for:

    compiler
    linker
    headers
    libraries
    Windows SDK
    tools
    architecture selection

The correct way to prepare the environment is to use Visual Studio's
Developer Command Prompt / VsDevCmd.bat.

This avoids manually maintaining MSVC paths and reduces the chance of
mixing compiler versions or SDK versions.

13. OPENMP HELLO WORLD
====================================================================

A test program named:

    openmp_test.cpp

was created.

The important portion was:

    #include <iostream>
    #include <omp.h>

    int main()
    {
        #pragma omp parallel
        {
            int thread_id = omp_get_thread_num();
            int thread_count = omp_get_num_threads();

            #pragma omp critical
            {
                std::cout << "Hello from thread "
                          << thread_id
                          << " of "
                          << thread_count
                          << std::endl;
            }
        }

        return 0;
    }

The program was compiled with:

    cl /EHsc /openmp openmp_test.cpp

It successfully executed using 8 OpenMP threads.

Example output:

    Hello from thread 2 of 8
    Hello from thread 0 of 8
    Hello from thread 1 of 8
    ...
    Hello from thread 7 of 8

The order was nondeterministic.

====================================================================
15. WHY OUTPUT ORDER WAS RANDOM
====================================================================

The threads are concurrent.

There is no guarantee that:

    Thread 0 prints first
    Thread 1 prints second
    Thread 2 prints third
    ...

Therefore output such as:

    Thread 2
    Thread 0
    Thread 4
    Thread 1
    ...

is normal.

The:

    #pragma omp critical

section prevents multiple threads from entering the printing section
at the same time.

It does NOT impose a particular execution order.

Important distinction:

    mutual exclusion
        !=
    deterministic ordering


====================================================================
16. OPENMP THREADS VS CPU CORES
====================================================================

The OpenMP test used 8 threads.

The CPU has:

    4 physical cores
    8 logical processors

Therefore:

    8 OpenMP threads
        !=
    8 physical CPU cores

The 8 logical processors arise from the CPU's hardware execution
capabilities, including simultaneous multithreading.

This distinction will matter later when benchmarking OpenMP programs.

The Hello World test was a functionality test, NOT a performance test.

22. WHY GLOBAL MSVC PATH MODIFICATION WAS AVOIDED
====================================================================

We deliberately did NOT permanently add the raw MSVC compiler

MSVC depends on more than the location of cl.exe.

    SDK mismatches
    difficulty switching Visual Studio versions

The VS Code terminal profile is therefore the cleaner approach.

35. FIRST CUDA PROGRAM
====================================================================

File:

    C:\Projects\Parallel\cuda_hello.cu

The program was intentionally tiny.

Final source:

    #include <cuda_runtime.h>
    #include <cstdio>

    __global__ void hello_from_gpu()
    {
        printf("Hello from GPU! Block %d, Thread %d\n",
               blockIdx.x, threadIdx.x);
    }

    int main()
    {
        hello_from_gpu<<<1, 4>>>();

        cudaError_t err = cudaGetLastError();
        if (err != cudaSuccess)
        {
            fprintf(stderr, "CUDA kernel launch failed: %s\n",
                    cudaGetErrorString(err));
            return 1;
        }

        err = cudaDeviceSynchronize();
        if (err != cudaSuccess)
        {
            fprintf(stderr, "CUDA execution failed: %s\n",
                    cudaGetErrorString(err));
            return 1;
        }

        return 0;
    }

====================================================================
37. CUDA PROGRAM CONCEPT — __global__
====================================================================

The declaration:

    __global__ void hello_from_gpu()

defines a CUDA kernel.

__global__ tells nvcc:

    This is a GPU-executed function
    that can be launched from the CPU.

Normal C++:

    void function()

would ordinarily execute on the CPU.

CUDA:

    __global__ void kernel()

creates GPU work that the CPU can launch.


====================================================================
38. CUDA PROGRAM CONCEPT — KERNEL
====================================================================

A CUDA kernel is essentially a function intended to execute on the
GPU.

The key difference is that CUDA allows many instances of the kernel
to execute in parallel.

For example:

    __global__ void kernel()
    {
        ...
    }

can be launched for:

    1 thread
    4 threads
    1024 threads
    millions of threads

depending on the workload and launch configuration.


====================================================================
39. CUDA THREAD HIERARCHY
====================================================================

CUDA organizes threads into blocks.

Conceptually:

    Grid
    |
    +-- Block 0
    |   +-- Thread 0
    |   +-- Thread 1
    |   +-- Thread 2
    |   +-- Thread 3
    |
    +-- Block 1
    |   +-- Thread 0
    |   +-- Thread 1
    |   +-- Thread 2
    |   +-- Thread 3
    |
    +-- ...

The entire collection of blocks is called the grid.

For the Hello World program:

    1 block
    4 threads per block

Total:

    1 * 4 = 4 threads


====================================================================
40. CUDA LAUNCH SYNTAX
====================================================================

The launch:

    hello_from_gpu<<<1, 4>>>();

means:

    1 block
    4 threads per block

General one-dimensional form:

    kernel<<<number_of_blocks, threads_per_block>>>();

For example:

    kernel<<<3, 4>>();

means:

    Block 0 -> 4 threads
    Block 1 -> 4 threads
    Block 2 -> 4 threads

Total:

    3 * 4 = 12 threads


====================================================================
41. blockIdx.x
====================================================================

Inside the kernel:

    blockIdx.x

identifies the current block's X coordinate.

For:

    hello_from_gpu<<<1, 4>>>();

there is only:

    Block 0

so:

    blockIdx.x == 0

for every thread.


====================================================================
42. threadIdx.x
====================================================================

Inside the kernel:

    threadIdx.x

identifies the thread's position within its block.

For four threads:

    Thread 0 -> threadIdx.x = 0
    Thread 1 -> threadIdx.x = 1
    Thread 2 -> threadIdx.x = 2
    Thread 3 -> threadIdx.x = 3

This is the basis for assigning different data elements to different
GPU threads.

This concept will become central to CUDA AXPY.


====================================================================
43. CPU VS GPU CONTROL FLOW
====================================================================

The CUDA program contains both CPU and GPU code.

The CPU executes:

    main()

The GPU executes:

    hello_from_gpu()

Conceptually:

    CPU
     |
     | main()
     |
     | launch kernel
     v
    GPU
     |
     +-- Block 0
         +-- Thread 0
         +-- Thread 1
         +-- Thread 2
         +-- Thread 3

This CPU/GPU division is fundamental to CUDA programming.


====================================================================
44. cudaError_t
====================================================================

CUDA operations can produce error/status values.

CUDA provides:

    cudaError_t

which is used to store the result of CUDA operations.

Example:

    cudaError_t err;

The variable:

    err

stores a CUDA status/error value.


====================================================================
45. cudaGetLastError()
====================================================================

The program performs:

    cudaError_t err = cudaGetLastError();

This asks CUDA for the most recent CUDA error state.

Then:

    if (err != cudaSuccess)

means:

    "Did the operation report something other than success?"


====================================================================
46. cudaSuccess
====================================================================

CUDA provides:

    cudaSuccess

as the successful status value.

Therefore:

    if (err != cudaSuccess)

means:

    if something went wrong...


====================================================================
47. cudaGetErrorString()
====================================================================

The program uses:

    cudaGetErrorString(err)

to convert a CUDA error code into a human-readable message.

This is useful for debugging.

Instead of only seeing a numerical status, we can get a message such
as:

    invalid configuration argument

or another descriptive CUDA error.


====================================================================
48. cudaDeviceSynchronize()
====================================================================

The program then executes:

    cudaDeviceSynchronize();

This is a major CUDA concept.

GPU work is generally asynchronous with respect to the CPU.

The CPU can launch GPU work and continue executing.

Conceptually:

    CPU                         GPU

    launch kernel ------------> start work
        |
        | CPU can continue
        |
        |
        +---------------------> GPU eventually finishes

cudaDeviceSynchronize() tells the CPU:

    "Wait until the GPU's outstanding work has completed."

It therefore creates a synchronization point.


====================================================================
49. WHY SYNCHRONIZATION MATTERS FOR ERROR CHECKING
====================================================================

The program performs two checks.

First:

    cudaGetLastError()

This checks the CUDA launch/error state.

Second:

    cudaDeviceSynchronize()

waits for GPU execution to finish.

Then the returned error is checked.

This is useful because some CUDA execution errors only become visible
when the CPU synchronizes with the GPU.

The two checks therefore help distinguish:

    launch/configuration problems

from:

    execution-time problems


====================================================================
50. fprintf(stderr, ...)
====================================================================

The program uses:

    fprintf(stderr, ...)

for errors.

    stderr

is the standard error stream.

This separates error output conceptually from normal program output.

The normal GPU message uses:

    printf(...)

while failures use:

    fprintf(stderr, ...)


====================================================================
51. return 0 VS return 1
====================================================================

Convention:

    return 0;

means successful program termination.

A non-zero return value generally indicates failure.

Therefore:

    return 1;

in the error paths means:

    stop the program and report failure.

70. MOST IMPORTANT LESSONS FROM CHAT 1
====================================================================

1. A driver is not the same thing as a toolkit.

2. nvidia-smi showing a CUDA version does not prove that nvcc is
   installed.

3. nvcc belongs to the CUDA Toolkit.

4. cl not being found in ordinary PowerShell does not necessarily
   mean Visual Studio/MSVC is missing.

5. MSVC should normally be initialized through Visual Studio's
   Developer Command Prompt/environment rather than by manually
   adding compiler paths globally.

6. Explicit x64 configuration matters.

7. VS Code is an environment/editor, not the compiler itself.

8. VS Code inherits environment variables from its parent process.

9. A VS Code terminal can be configured to initialize MSVC correctly.

10. OpenMP is a programming model, not a GCC-only feature.

11. OpenMP thread count should not be confused with physical CPU core
    count.

12. Concurrent output does not imply deterministic execution order.

13. CUDA programs contain both host (CPU) and device (GPU) code.

14. __global__ identifies a GPU kernel launchable from the CPU.

15. CUDA organizes execution using grids, blocks and threads.

16. <<<blocks, threads_per_block>>> specifies a kernel launch
    configuration.

17. blockIdx.x identifies a block.

18. threadIdx.x identifies a thread within its block.

19. GPU execution is generally asynchronous with respect to the CPU.

20. cudaDeviceSynchronize() allows the CPU to wait for GPU work.

21. Error checking is an essential part of CUDA programming.

22. A tiny Hello World program is valuable as a known-good diagnostic.

23. Toolchains should be verified incrementally rather than assuming
    that a successful installation means the whole system works.

24. GCC was deliberately postponed so that multiple compiler
    environments would not be introduced at the same time.

25. The most important final result is not merely that CUDA installed;
    it is that a CUDA kernel was actually executed on the RTX 3050.
